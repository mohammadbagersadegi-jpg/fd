## 3. Round-1 enemy-load-cue stream

Round 1's stream is pointed at by `$1B036` (`off_1B036`, indexed by `Level`)
and stored at `$1B046`. It is Nemesis-compressed: 402 bytes in the listing,
448 bytes decoded, header `$000E`. All eight round streams decode to exactly
the size the game's own offset table and the recompilation analysis state
(`reference-all-rounds-census.json`).

Decoded stream: `analysis/elc/round1.bin` (regenerated by the script, not
committed).

### 3.1 Block framing

A wave block is three length-prefixed batch columns, then a timed list ending
in `$0099`, then a length-prefixed deferred section whose payload ends in
`$99 00`. The consumer is `EnemySpawn_Scene` (listing 777) for the three batch
columns and `loc_784` (listing 945) for the timed/deferred lists; both advance
`$FFFFFC14 (Cur_ELC_Adr)`.

| Block | Batch records per column | Timed | Deferred | Stream range |
| ---: | --- | ---: | ---: | --- |
| 1 | 1 / 3 / 2 | 2 | 2 | `0x000–0x04B` |
| 2 | 3 / 3 / 4 | 3 | 3 | `0x04C–0x0BD` |
| 3 | 3 / 5 / 4 | 3 | 3 | `0x0BE–0x13B` |
| 4 | 3 / 3 / 4 | 3 | 2 | `0x13C–0x1A7` |

Totals: **59 records** = 38 batch + 11 timed + 10 deferred; 42 are
one-player records, 17 are two-player-only.

## 4. Spawn model (the part that was wrong before)

### 4.1 Code path

`Load_Enemy_Into_RAM` (listing 1779) runs once at level start:

1. Nemesis-decode the round stream into `$FF6800 (ELC_Buffer)`.
2. Pick the round's five-entry descriptor table (`off_1C1C4` → round 1:
   `off_1C1D4`), read the 4-byte cursor (`$FF6800`) into `$FFFFFC14`, then the
   2-byte geometry selector.
3. `word_1C1BC[selector]` gives the stride (`$FFFFFB20`) and the base
   (`$FFFFFB12`). Round 1 uses selector 0 → stride 1, base `$0300`.
4. `Update_Enemy_Pal` consumes the 5-byte palette descriptor that follows.
5. `Init_Enemy` is called **three times**, with
   `add.b d2,($FFFFFB12).w` between the calls.

`Init_Enemy` (listing 1557) per column:

```
move.w  (Cur_ELC_Adr),d5        ; count
loop:   read type, $40, $41, $49, x_low, $15
        d0 = ($FFFFFB12 & 0xFF00)
        d0 = (d0 & 0xFF00) | x_low      ; move.b (a2)+,d0
        XPos(a1) = d0                   ; word write into a dword field
```

### 4.2 The byte-order trap

`$FFFFFB12` holds the base **word**; the byte at that address is its **high**
byte on the 68000. `add.b d2,($FFFFFB12).w` with `d2 = 1` therefore adds
`$0100`, not `1`. The base walks `$0300, $0400, $0500` for block 1, and keeps
walking across blocks because it is never reset:

```
X_world = 0x0300 + 0x0100 * (3 * (block - 1) + column) | x_low
```

(The script writes `column_index = 3*(block-1)+column`; the high byte of the
base and `x_low` never overlap, so `|` and `+` are equivalent here.)

This matters: a naive "base + 0x100 × column, reset every block" model puts
blocks 2–4 three to nine 256-px bands too far left.

### 4.3 Prediction test against runtime data

The autoplay project documents two round-1 phone-booth positions from its own
recompiled runs. The model must reproduce them without any fitting:

| Runtime note (third party) | Parsed record | Model |
| --- | --- | --- |
| "the first real breakable is a type-`$11` booth at **(2016, 32)**" | block 2, column 1, `x_low $E0`, depth 32 | `0x0700 | 0xE0 = 2016` ✅ |
| "…at the type-`$11` booth at **2920**" | block 3, column 2, `x_low $68`, depth 32 | `0x0B00 | 0x68 = 2920` ✅ |

Both match to the pixel, including the 32-px depth. Seven booth positions come
out of round 1: `2016, 2192, 2472, 2920, 2960, 3000, 3672` at depth 32 (one
further booth at `1304`-band position is two-player-only and excluded).

### 4.4 Timed and deferred records

`loc_784` (listing 945) walks the timed list: a word delay, then a 6-byte
record. Rejected records (difficulty too high, or two-player-only outside
2-player mode) are skipped with `lea 6(a2),a2` **after** the delay word, so the
stream stays aligned. An accepted entry stores `delay & $7FFF` in
`$FFFFFB16`, which counts down and then calls `sub_C60`.

`sub_C60` (listing 1511) copies the record's byte 4 to object `+$15` and uses
byte **5** as the **edge selector**: byte 5 = 0 → `X = cam_x + $148` (right
edge); byte 5 ≠ 0 → `X = cam_x - 8` (left edge). Round 1's 11 timed entries use
delays of 16/32/48/64/80/112 ticks and split 6 left-edge / 5 right-edge
(`reference-stage-01-timeline.csv`, column `side`). They are therefore
*camera-relative* reinforcements, not fixed positions; the deferred entries
split 6 left / 4 right.

The deferred list is spawned by a different path: `loc_936`/`sub_966` reserve a
palette, `loc_B76` takes `$FFFFFC28 (the cursor after the delay word)`, calls
`sub_C60`, and then compacts the remaining list backwards
(`move.l (a2)+,-$A(a2)` at listing 1434) so the next free slot can re-read it.
That compaction is why the same list survives across frames without a
length-prefixed re-read; it also means the *frame* on which a deferred object
appears depends on slot availability, not only on the stream order.

The deferred section that follows the `$0099` terminator is a flat array of
6-byte records ended by `$99`; its length word is what `loc_790` skips. Its
records are also camera-relative when spawned.

## 5. Camera track and wave gating

`sub_19570` (listing 45640) consumes `$FFFA0D` bit 0, increments `Scene`,
indexes `word_195D8` (listing 45685) and writes the value to camera `+$1A`
(max X) for rounds 1–7, then copies the current camera X into `+$1E`
(min X). `$FFFF` ends the stage (restores `Scene`, sets `FadeOut_Flag`, starts
a `$40` palette fade).

Round-1 gates:

| Scene | Max X | Decimal | Meaning |
| ---: | ---: | ---: | --- |
| 1 | `$04C0` | 1216 | first corridor opens |
| 2 | `$07C0` | 1984 | second |
| 3 | `$0AC0` | 2752 | third |
| 4 | `$0DC0` | 3520 | fourth |
| 5 | `$10C0` | 4288 | fifth |
| 6 | `$13C0` | 5056 | last corridor |
| 7 | `$FFFF` | — | end of stage |

Corroboration from the autoplay notes (third-party runtime): the player is
clamped to `camera_x + $20 … camera_x + $120` while a wave is alive, and the
notes give "stops at world x=1504" for the first gate — `1216 + 0x120 = 1504`
exactly — and "clamped at x=3036" at the third gate — `2752 + 288 = 3040`,
within 4 px. This independently confirms both the gate table and the clamp.

Spawn bands line up with the gates: block 1 sits at `$0300–$05FF`, block 2 at
`$0600–$08FF`, block 3 at `$0900–$0BFF`, block 4 at `$0C00–$0EFF`; each band
starts `$1C0` before its gate.

`Scene` is also the index into the per-round resource/palette descriptors
(`off_1C1C4`, via `EnemySpawn_Scene`'s `Scene + 1` lookup). Round 1's five
6-byte descriptors are:

| Lookup | Bytes | Reading |
| --- | --- | --- |
| scene 0→1 | `00 01 02 00 00 03` | palette lines 0/1/2, enemy set 0 |
| scene 1→2 | `00 01 02 00 00 03` | same |
| scene 2→3 | `00 01 03 00 00 06` | third slot changes |
| scene 3→4 | `00 01 04 00 10 00` | enemy palette set 1 (`$10` nibble) |
| scene 4 | `00 00 00 00 00 00` | all-zero terminator |

`Update_Enemy_Pal` consumes 4 bytes into `Pal_Correct`, reads byte 4 as the
palette selector (bit 7 = boss table, high nibble = enemy palette set) and uses
the low nibble of byte 5. The exact palette RAM contents are not decoded here.

## 6. Boss / final-wave tail

After block 4's deferred section the stream continues with bytes that do **not**
follow the wave-block framing. For rounds 1–6 the tail starts as
`00 10 <type> …`, i.e. delay 16 followed by a 6-byte record whose type matches
the round's boss in the `$1C378` art/palette table:

| Round | Boss (from `$1C378`) | First tail type | Second record |
| ---: | --- | --- | --- |
| 1 | Antonio | `$56` (then `$D6`, the 2P-only bit set) | delay 16 |
| 2 | Souther | `$55` (then `$D5`) | delay 16 |
| 3 | Abadede | `$30` (then `$B0`) | delay 16 |
| 4 | Bongo | `$57` (then `$D7`) | delay 16 |
| 5 | Onihime & Yasha | `$58`, `$58` | both delay 16 |
| 6 | Souther (pair) | `$55`, `$55` | both delay 16 |
| 7 | Abadede | `FF FF FF FF FF FF` sentinel | — |
| 8 | Mr. X | `$33` | delay 1 |

Round 5's two identical `$58` records at delay 16 fit the twins; round 6's two
`$55` records fit the Souther pair. That is a strong pattern, but the *framing*
after the first two pairs is unresolved (see §8).

Round-1 tail, all 24 bytes:

```
00 10 56 00 04 00 10 00  00 10 d6 01 05 00 10 01  00 99
00 02 99 00 6a 00
```

Reading: `delay 16 → $56`, `delay 16 → $D6`, `$0099` ends the timed list,
`$0002` + `$99 00` is an empty deferred section, and `6a 00` is unexplained
(UNKNOWN). The `$D6` record has the two-player-only bit, so in 1P mode only the
first `$56` boss spawns — which is consistent with a single Antonio.

## 7. What the visuals can and cannot say yet

Static facts (`reference-stage-01-visual-inventory.json`):

* display 320 × 224 (VDP register 12 = `$81`, H40);
* two 64 × 32-cell scrolling planes (`R16 = $01`), primary block map at
  `$FF0000`, secondary at `$FF2000`, metatile tables at `$FF4000`/`$FF4800`,
  collision class map at `$FFA000`;
* round package rooted at `$5F5B8`; three compression families in use
  (Nemesis for ELC/art, Enigma for metatiles, Kosinski for block maps);
* music id `$81` for round 1.

Blocked without the ROM: palette RGB values, tile pixel content, sprite scale,
layer composition, texture density, signage, prop silhouettes. The addresses
are known, but decoding them requires the cartridge image (or a lawful dump),
which this environment does not have. The dossier therefore stops at
"where the data is", not "what it looks like", and Gate A cannot be fully
signed off.

## 8. Contradictions and unknowns

1. **Scene vs. block count.** `EnemySpawn_Scene` refuses to spawn when
   `Scene >= 3` for rounds 1–4, yet round 1 has four wave blocks. Either the
   guard is evaluated before `Scene` is incremented, or block 4 belongs to the
   final/boss pipeline. Not settled. Blocks 1–3 are confirmed by the two booth
   predictions; block 4 is `HYPOTHESIS`.
2. **Tail framing.** The first two delay/record pairs are readable; the rest
   of the tail contains repeated 6-byte groups and length-prefixed sections
   that do not parse as wave blocks. Round 1 leaves `6a 00` unconsumed, round 7
   has a `FF FF FF FF FF FF` group. UNKNOWN.
3. **Palette semantics.** `Update_Enemy_Pal` reads `Pal_Correct` (4 bytes),
   a selector byte and a nibble, but the mapping to actual CRAM colours was not
   decoded. No palette claims are made.
4. **Object type names** other than the autoplay-documented enemy types and
   `$11`/`$19` are unknown. Props are listed by ID only.
5. **Our own runtime.** Never performed. Every position/behaviour statement
   above is static, or a *third party's* runtime observation used as a
   cross-check and labelled as such.
